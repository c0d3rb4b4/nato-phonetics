## Delivery model

P00–P10 are agent implementation phases. P00 was added after Run 02 so existing phase IDs and evidence remain stable; it is the required build foundation. R25 adds priority P05.6–P05.8 after Run 03 without renumbering earlier tasks. **M11 is the only phase containing human/manual work**, including product decisions that genuinely require the owner, credentials, physical-device checks, listening review and release acceptance. Agents prepare its artifacts and record evidence; they must not claim human checks have passed.

M11 is one phase with two checkpoints, not separate gates for every implementation phase: prerequisites can be supplied when necessary, and the acceptance pass happens against the integrated candidate. This lets manual work stay together without creating a circular dependency in which a credential needed for implementation is withheld until implementation is finished. Routine engineering choices, automated browser checks, builds, screenshots and fix verification belong in P00–P10.

An implementation phase may be **agent-done** while its linked manual checks remain pending. That permits dependent implementation to continue, but does not make the issue resolved or the release ready. Failed manual checks reopen the owning implementation task; the corresponding retest stays in M11.

### Working assumptions

- Remove Expo completely in P00: use React Native with repository-owned Android/iOS projects, replacement navigation/platform adapters and an independent web build. Preserve local-first storage; do not add accounts, a backend or analytics to deliver this scope.
- Builds must run locally or on self-hosted CI through Gradle and Xcode, without Expo/EAS CLI, accounts, tokens, subscriptions or hosted build quotas. Use Eclipse Timer's local execution/artifact patterns as a reference, but replace its remaining Expo/EAS steps. Platform signing and store access are separate M11 inputs; this requirement does not promise that store distribution has no fees.
- Treat iOS, Android and web as planned targets, because F10 is included. Record actual OS/browser/engine support during implementation; unsupported capability must be explicit.
- Treat NATO tiles as a fixed design composition: preserve the original alphabet's 11:15 portrait ratio, rounded corners, header/body structure and per-letter colors. Share exact geometry and typography across platforms; responsive layout changes columns/outer spacing or uniformly scales the whole tile, never its proportions or individual text styles. R25/P05.6–P05.8 define and verify this contract while preserving large-text accessibility.
- Preserve voice selection. Separate canonical text, pronunciation guides and spoken representation. Start with a replaceable device-speech adapter and honest provider-dependent privacy/offline wording; do not require recordings before useful implementation can proceed. If reviewed recordings are selected, acquisition/rights/listening decisions are tracked in M11.
- Spoken-answer practice is optional to use, but its implementation is in scope. Request microphone access only on explicit use, prefer on-device recognition when available, and do not quietly send audio to a new cloud service. A denied/unavailable engine must leave other practice modes working. A permanently unavailable target needs an owner-approved support decision, not a fake completed feature.
- Web offline support covers an explicitly defined app shell and local learning data. Speech/recognition provider connectivity is a separate capability and must be described accurately.
- Use reasonable reversible defaults. Put genuinely missing owner inputs into M11 and proceed with independent work. Record a changed assumption with its reason and affected tasks. Reprioritization and parked residuals do not imply scope removal or acceptance.
- Publishing, paid services, account setup and release acceptance belong in M11 when required. Prepare a concrete candidate and instructions first; do not invent a need for approval for ordinary local implementation.

## Impact triage and investigation limits

**Current priority amendment — 17 November 2026, after Run 07.** Requested evidence review: [findings and per-run assessment](DELIVERY_PRIORITY_REVIEW.md). This section governs current scheduling when older execution records or task descriptions say all of P05 must finish first. The original portrait design requirement remains; its implemented shared component is the foundation for subsequent features. Reprioritization changes order and blocking scope, not completion, support or release acceptance.

For every new failure, record: owning task; reproducible scenario/platform/settings; actual user consequence; confidence and unrun evidence; workaround/state risk; effort including verification; and the exact flow/task it blocks. Separate **severity**, **scenario reach** and **certainty**. Do not infer prevalence from simulator test counts. Large-text accessibility, lost input/state, incorrect learning/audio, unusable navigation, false privacy claims and reachable security/build failures keep P0/P1 treatment where warranted, even in less common scenarios. A measured raster fringe with readable text and intact geometry can be P3. An unknown cause is not proof of harmlessness.

**Blocking rule:** unfinished work blocks consumers only when the required capability is missing or broken in that consumer. P06/P07 may use delivered P05 controls/tiles while P05 stays active. Their changed-flow readability, concealment, focus, input and audio checks still apply; a reproduced P05.2 failure keeps the affected accessibility acceptance open. Pixel-polish failures alone do not block implementing or validating unrelated features. P10 preparation tasks may also proceed independently; final integrated gates and M11 remain required. Never label a failing check as passing, weaken the font/design contract, suppress native scaling or remove a supported target to obtain progress.

**Investigation boundary:** forecast a concrete diagnostic question, smallest discriminating experiment, expected implementation/verification work and a stopping checkpoint. At that checkpoint, continue only with new evidence supporting a plausible repair and an updated impact/effort forecast. Repeating a falsified hypothesis or broadening matrices without new risk is not progress. Before starting a framework source build, dependency upgrade or new renderer probe, compare its cost with the next useful feature. If no repair is established, park a low-impact issue with a re-entry trigger; retain a genuine P1 as an affected-flow blocker and switch to independent valuable work when practical. Do not spend another whole run on the same inconclusive boundary without an explicit new rationale. This limits investigations, not the number of phases in a run.

**Verification proportional to change:** preserve all existing evidence. Reuse qualified unchanged results, run meaningful checks for affected behavior and capture changed flows on supported targets. Expand the matrix only for a new observed risk or a renderer/font/shared-layout change. Keep stable all-letter/native/window checks historical until relevant changes invalidate them. Diagnostic red results stay red with explicit milestone policy; a nonblocking disposition is not a passed gate. Documentation-only reviews need link/status/source-preservation checks and a screenshot inapplicability record, not new builds or app images.

## Execution contract for every reusable-prompt run

### Resume and forecast

1. Find the app root whether the workspace is `apps/` or `nato-phonetics/`. Read applicable instructions, this plan, the review's current delivery section and relevant source. Inspect the working tree; do not discard user/uncommitted changes or repeat completed work blindly.
2. Reconcile recorded state with actual code/evidence. Apply the latest impact triage and task-level dependencies; partial work is not automatically the highest-value next work. Resume it first when user consequence and verification cost justify it. A stale checkbox is not proof of completion. Record discrepancies and repair the ledger.
3. Forecast the next dependency-ready work using scope, touched modules, uncertainty, integration risk, available tools, expected test/build duration and the available execution/context budget. Include time for validation and documentation; do not invent a numeric budget the environment does not expose.
4. Choose a coherent batch that can be finished and verified. **Do not fix a number of phases and do not default to one.** Complete multiple phases when the forecast supports it; a large phase may need more than one run. State the selected IDs and rationale, then implement rather than stopping at the forecast.
5. Reforecast after each completed phase or investigation checkpoint. Triage new failures by impact/confidence before selecting them; record parked residuals and re-entry triggers in the engineering queue. A new strict diagnostic failure does not automatically outrank eligible core features. Continue into further eligible phases when practical, without asking for confirmation at routine phase boundaries. Parallelize independent work when useful. Keep implementation, tests and evidence together.

### Execute, verify and stop honestly

- Implement the chosen work, resolve blocking failures and run the checks appropriate to the change. Keep nonblocking failures visibly open with evidence, priority and re-entry triggers; do not broaden an unrelated gate or call it passed. Apply the investigation boundary before another framework/raster cycle. After available gates pass, do not repeat broad tests without a new change/failure/unresolved concern.
- M11 is the sole human-task queue. Prepare the exact missing input, candidate or test instructions before requesting owner action. Continue independent work while inputs are pending; never treat elapsed time or silence as approval.
- Stop at a coherent boundary when no eligible work remains, a real constraint prevents progress, or the remaining execution budget is needed for verification and a reliable handoff. Do not stop solely because a preset phase count was reached.
- If a selected phase cannot finish, leave it `active` or `blocked` with its precise completed tasks, failing/unrun checks, cause and next action. Do not substitute documentation, a placeholder or mocks for required implemented behavior.
