# Web offline shell and updates

Implemented in Run 16 for the independent production web build. [Evidence](evidence/run16/README.md), [release runbook](RELEASE_RUNBOOK.md). This is app-shell caching, not a microphone feature, speech-provider guarantee, install prompt or publication.

`npm run export:web` emits thirteen route HTML files, hashed application code/three bundled fonts, favicon, `offline-manifest.json`, `service-worker.js` and a reference `_headers` file. Each resource has a SHA-256 digest. The shell ID hashes the sorted resource inventory, route map and worker template; identical inputs give the same ID. A generated worker is syntax/behavior checked by the worker tests and exercised by the real production browser suite. The template contains build substitutions and is excluded from direct ESLint parsing.

## Availability and storage

A first connected visit over HTTPS (secure loopback for local checks) registers the root worker. It fetches and validates every listed resource before completing installation. Menu → Web availability shows preparing, ready, update-waiting, retry or unavailable guidance. An active worker checks that every resource is present before reporting ready; Check for web update / Retry offline setup can repair an evicted resource from the server after reconnection. A timeout or failed verification reports a failure. Partial first installs cannot claim offline readiness.

After readiness, offline navigation can load reference, converter, practice, settings and progress routes. In Firefox 159, quitting the whole browser with a waiting update can interrupt this path even when the app cache is complete. Follow the connected update steps below before going offline. Extensionless, `.html`, query-bearing and unknown app navigation use the pinned route shell; unknown routes still show Page Not Found. A never-visited site needs a connection. Browser eviction, private-mode restrictions and clearing site storage can remove availability; the app cannot promise permanent retention or override those controls. No home-screen install flow or persistent-storage permission is added.

CacheStorage names are `nato-shell-v1-<SHA-256 shell ID>`. Contents are only public build resources, never converter text, responses, audio, progress or provider traffic. Only same-origin listed GET assets and app navigations are intercepted; other requests, POSTs and external/provider requests pass through. Missing JS/font/image requests do not receive the app HTML. An evicted pinned resource fails with HTTP 503/reconnection guidance rather than mixing server versions. Local learning data remains in `nato.progress.v1`, preferences in `nato.preferences.v1`, with the existing independent reset/deletion controls. Clearing Progress or Reset Preferences keeps the shell cache; clearing all browser site data removes it and local records. No account, new provider, telemetry or native permission is added.

## Updates and rollback

An active worker always serves its own verified build, even online. Check for web update checks the stable worker URL; browser visits also trigger their normal update checks. A complete changed worker waits until every window controlled by the old worker has closed. There is no `skipWaiting`, forced reload or `clients.claim`. Reloading one window while another remains open keeps the current version. When Menu shows an update, finish the round, save pending answers and copy any draft. Leave another browser tab open, close every NATO Phonetics tab or window, then reopen Menu while connected. Wait for “Offline copy ready” before disconnecting. Firefox 159 passed a subsequent cold offline launch with the same saved answer after this sequence. [Observed failure and recovery](evidence/run41/firefox/README.md). Rounds/drafts/unsaved events are still memory-only and deliberately close with the page. Waiting is not a frozen-page or legacy-client upgrade pass.

On normal activation, only older `nato-shell-v1-*` caches are removed; unrelated caches and local records are retained. Failed installation/download/digest verification leaves the active shell intact. Retry handles a failed first installation as well as an update. Deployments must keep complete directories and switch atomically: if the server changes while the worker downloads resources, digest mismatch rejects the mixed build. Rollback serves the previous complete directory and follows the same close-all/waiting lifecycle, without clearing user data. For a cache repair, the server must still have the active build's exact resources; if it no longer does, use the completed update instead.

Legacy windows predating Run 15 remain a separate deployment migration risk: neither the worker nor updated Web Locks can make already executing old code coordinate writes. Finish/save or explicitly discard in-memory work, close every legacy window and reopen the current complete build before claiming an upgrade. [Progress rules](LOCAL_PROGRESS.md) retain generation/schema/deletion safety.

## Local verification and support limits

Use a separate origin/port for development and production previews so an older production worker cannot intercept a development navigation. Development `npm run web` does not register a worker. For example, keep development on 8080 and preview production with `PORT=8090 node scripts/serve-web.cjs dist`. For a reused test origin, remove its worker/cache through browser developer tools when deliberately starting fresh; do not clear real user data to fake an upgrade pass.

Run `node scripts/verify-offline-browser.cjs dist artifacts/offline-browser` with the isolated Puppeteer setup in README. It exercises actual workers, caches, production pages and storage. Update fixture B is explicitly the same production JS with an HTML root marker and a recomputed shell inventory; it tests lifecycle/version consistency, not an invented separately shipped application. Real browser process restart uses a persistent test profile. Network is disabled both through browser emulation and the server, so worker requests cannot quietly reach the test origin.

Run 16 qualifies Edge 157 on macOS loopback, including 320px dark/200% text. Safari/Firefox/other runtime, frozen-process restoration, legacy hosted upgrades and actual HTTPS host headers/routing remain engineering qualification in P08.3/P10.4/.5; no target or support exception is approved. Physical browser/provider/airplane-mode acceptance remains M11.6/.7. Native apps keep their existing bundled shell; the native policy only removes the obsolete claim that web caching is unimplemented.

The default waiting lifecycle follows the [service worker lifecycle documentation](https://web.dev/articles/service-worker-lifecycle); secure-context/install/cache behavior is described in [MDN's service worker guide](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API/Using_Service_Workers) (checked 18 November 2026). Actual repository behavior and evidence govern the claims here.
