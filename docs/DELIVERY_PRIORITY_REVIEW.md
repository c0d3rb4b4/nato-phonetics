## Finding

Development has delivered substantial useful foundations, but Runs 05–07 show diminishing returns from treating every P05 fidelity check as a prerequisite for all feature UI. The main drift is in scheduling and dependency rules. Restoring the portrait design was explicitly requested and justified; continuing to block sessions/results and converter completion on a faint raster fringe is disproportionate to the demonstrated user impact.

Keep correctness, readable controls, accessible core flows, audio ownership, honest privacy claims and reproducible builds at the front. Preserve the delivered tile design. Move the remaining maximum-size iPhone ink-edge discrepancy to P3 polish, retain its failed measurements, and allow independent feature work while P05 remains partial. Android's internally clipped labels remain P1; being encountered at large text does not make an accessibility defect unimportant.

This is an evidence-based engineering assessment, not a usage study. The evidence has no comparable per-run effort accounting, user-frequency telemetry or physical-device acceptance. Run count, test count and screenshot volume cannot establish hours wasted, prevalence or release readiness. This review makes no dependency-version or security claim beyond the dated local records.

## Why the plan encouraged drift

1. **One phase mixed different risks.** P05 combined invisible ink fringes, actual unreadable controls, missing platform evidence and the requested design restoration under the same P1 label. One unchecked item blocked every downstream UI phase.
2. **Phase completion replaced actual dependency analysis.** The verified shared tile/audio/controls already suffice for session integration, but P06/P07 waited for every P05 check. Even candidate preparation was broadly tied to all earlier phases.
3. **Failed measurements automatically became next work.** The plan required honest failure reporting, but did not require a separate impact/priority decision or define a parked engineering queue.
4. **Inconclusive investigation had no explicit escalation boundary.** Android work repeatedly retained state yet failed text equivalence, and the next proposal grew to a source-built framework. The plan needs to require new discriminating evidence and opportunity-cost review before expanding that work.
5. **Evidence could become the deliverable.** More native contexts and images improve confidence when they test a risk. Repeating the stable matrix or broadening it to chase a tiny residual can consume the next feature's implementation/verification allowance.

## Adopted operating rules

The current [delivery plan](DELIVERY_PLAN.md#impact-triage-and-investigation-limits) owns these rules. Record every new defect's reproduction, platform/settings, user consequence, evidence confidence, workaround, effort and affected dependency. P0/P1 applies to lost/wrong data, unusable core controls, accessibility failure, false privacy claims and demonstrated security/build problems; rarity alone cannot lower severity. Mark uncertainty as uncertainty. Pure raster polish with usable text can be P3.

Only the affected task/flow/support claim is blocked. A parked issue has an owning P-task, priority, evidence, explicit re-entry trigger and next check in the plan's engineering queue. It stays open; it is not moved into M11 or counted as delivered. Keep strict diagnostics red and make their milestone-blocking policy explicit. No threshold, supported target, original design requirement or final release acceptance is waived by this review.

Forecast investigation and verification together. At the declared checkpoint, an inconclusive result must produce a failing reproduction or a narrower causal hypothesis. Repeated failures without new discriminating evidence require parking a low-impact issue, or recording a real affected-flow P1 blocker and switching to independent valuable work. A source-build/upgrade or another expanded matrix needs a new impact/effort decision. This is a per-issue investigation boundary, not a fixed phase count.

Next implementation should deliver **P07.2/.4 UI/audio integration**, while scheduling a bounded **P05.2 Android cold/live readability investigation**; **P06.1/.2** is the next independent useful slice. Select the feasible combination from actual capacity. Preserve the large-text release failure until repaired, then proceed to drills/progress and support/offline/release work. Do not resume the P3 iPhone fringe as the default next task.
