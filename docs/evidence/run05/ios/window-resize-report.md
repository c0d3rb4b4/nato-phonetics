# Actual iPad window resizing

17 November 2026. **Tile resize assertions pass; visual inspection identifies a separate window-header overlap.** The unchanged final iOS candidate was exercised in an actual iPadOS window, then restored to full screen. This is not simulator canvas scaling or a display-size override.

The separate [XCTest source](window-resize.swift), generated by [window-resize.rb](window-resize.rb), ran on iPad Pro11-inch(M5), iPadOS26.2,2× density, default text size. The scoped follow-up belongs to **P05.2**. The custom header in `app/_layout.js` uses `SafeAreaView` with top/left/right edges, then places the Home button in a 48-point slot with 8-point horizontal padding. The installed `react-native-safe-area-context` provider reads UIKit's ordinary `safeAreaInsets`; it does not request the iPadOS 26 corner-adapted layout region. Home occupies the same leading slot on every non-home route. The overlap is observed on Alphabet; extension to other non-home routes is a code-based inference awaiting captures. There is no Back button in this header. Menu's **Back to App** button is in the screen body below the header; its overlap or tap failure was not observed or tested here. The right-side menu button also needs a real tap check before navigation acceptance.

Apple's [WWDC25 UIKit adaptation guidance, 12:21–13:37](https://developer.apple.com/videos/play/wwdc2025/282/) recommends a corner-adapted layout guide for custom bar content. The available iOS 26 SDK exposes `UIView.layoutGuide(for: .margins(cornerAdaptation: .horizontal))`, `.safeArea(cornerAdaptation: .horizontal)`, and `edgeInsets(for:)`. The smallest robust implementation to investigate is an iOS 26 header-specific native adapter that supplies these live corner-adapted insets to the existing React header, retaining ordinary safe-area behavior on older iOS and other platforms. It must respond to scene resizing; a fixed padding value cannot express this layout region. The [scene window-control style](https://developer.apple.com/documentation/uikit/uiwindowscene/windowingcontrolstyle) alone is not a demonstrated fix: Apple says custom content should account for the control regardless of style. No adapter or speculative style/padding change was implemented in this batch.

Use app-scoped accessibility queries for the app controls, and capture the OS traffic lights separately so the test cannot accidentally target system close/minimize controls. Recheck a second small window size, both iPad orientations, larger text, and the unaffected iPhone header. Repeat tile dimensions/reflow after the inset change. Preserve this run as pre-fix evidence. The current test drags only the OS window's bottom-right handle using coordinates relative to `app.windows.firstMatch`; it never presses the traffic lights or asserts Home/Menu taps.
