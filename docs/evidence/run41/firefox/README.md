## Changed user flow

Menu now asks the learner to finish the round, save pending progress, copy drafts, leave another browser tab open, close every app tab or window, and reopen Menu while connected. Once Menu confirms that the offline copy is ready, the learner can disconnect. The new `handoff` scenario immediately reopens Menu, using the visible ready confirmation. It then quits the process, stops the origin and disables browser networking. Its first cold navigation received the exact forward progress HTML with HTTP 200 and an active controlling worker. The saved answer, preferences, unrelated storage and unrelated cache entry matched their pre-update values. All three reported groups passed on the integrated archive. ## Process-quit failure

- **Forecast and trigger.** Previous runs could see an active worker from a document that lacked control. The retained Firefox binary supports browser network and worker telemetry. Budget one native startup trace on the hosted archive, then fork the same closed profile to test first offline navigation if the online gate fails again.
- **Hosted archive.** The closed profile contained a persisted service-worker registration, but its script-cache key had no named entry in Firefox’s internal script storage. Both online documents lacked a controller. Gecko issued two HTTP GETs for the progress navigations. The saved answer remained visible. After the online process exited, the newly persisted registration had a matching worker script. [Closed profile](hosted-profile-before-first-navigation.json) · [Gecko excerpt](gecko-online-excerpt.log) · [After the online process](hosted-profile-after-online-process.json)
- **First offline fork.** An untouched copy of the closed profile failed its very first offline navigation with `NS_ERROR_OFFLINE`. Firefox showed its own offline page before the application loaded. Run 39’s subsequent offline launch used a different point in profile history. [First offline result](first-offline.json) · [Browser error](../screenshots/web/firefox-first-offline.png)
- **Connected recovery.** Reconnecting the failed fork to Menu produced the ready confirmation. The next online visit to progress had an active controller. After a process quit, a cold offline launch served the forward shell and the original saved answer. [Recovery trace](recovery.json) · [Recovered answer](../screenshots/web/firefox-recovered-offline.png)
- **Reforecast.** The first offline failure affects access to the entire shell when quitting during a waiting update. Keep P1 on that flow. Replay on the integrated archive and compare the registration and both worker-script entries immediately before and after closing the process. Check a user-facing route around the failing transition independently.
- **Integrated archive.** While the worker was waiting, the registered UUID and a second UUID both had matching script records. Across process close, the registration bytes remained identical while its named script-cache entry disappeared. The other internal script remained, together with the forward application shell. The closed database had a zero-byte WAL. Both new online documents again lacked control. The direct offline fork again failed with `NS_ERROR_OFFLINE`. App cleanup only selects names beginning with `nato-shell-v1-`. Firefox stores its worker scripts in a separate internal namespace. The exact internal shutdown code path and frequency outside this runtime remain unknown. ## Reproduction and limits

Build with `WEB_OUTPUT_DIR=<dedicated-directory> node scripts/build-web.cjs` and run `node scripts/package-web.cjs <directory> <new-archive>`. On a Linux host with the pinned browser and Caddy, run `node scripts/verify-web-host.cjs <archive> <new-output> firefox handoff`. The existing `firefox process` command retains the strict independent process-quit gate.

To reproduce the diagnostic on a disposable checkout, apply [the observer patch](observe-profile.patch) to the final host driver. Set `FIREFOX_PROFILE_PROBE` to the absolute path of [profile.py](profile.py) and run the process command. The observer saves the pre-reopen profile and enables Gecko HTTP and worker telemetry only on the second launch. Read a snapshot with `python3 profile.py <profile>`. Run `node first-offline.cjs <process-output> <new-offline-output>` with Caddy stopped. To test recovery after the first offline failure, run `node recover.cjs <process-output> <offline-output> <new-recovery-output>`. The recovery starts Caddy on the original loopback port. [Offline probe](first-offline.cjs) · [Recovery probe](recover.cjs) · [Gecko logging](https://firefox-source-docs.mozilla.org/xpcom/logging.html)

Two initial private runner copies omitted first the Caddy configuration and then the package metadata. They stopped before the restart. A live SQLite reader also hit Firefox’s exclusive database lock. The final observer copies the database and WAL into a private temporary directory, verifies both source digests remain stable, then queries the copy. The application and the strict gate ran without changes to their behavior during observation. [Live-reader failure](live-database-lock.json)

The bare process quit remains a failed P10.4/.5 acceptance path. The connected handoff is verified on this Firefox build. Re-enter on a Gecko shutdown-persistence or worker lifecycle change, with the same pre/post registration-to-script check and an actual first offline navigation. Screen readers, branded OS/browser reach and release acceptance retain their existing M11 scope. All seven Firefox captures were inspected. The waiting message appears in full at 1280×900/light and 320×568/dark. The two browser error screens are diagnostic evidence. This web-only change has no native UI capture.
